
# TWM — Technical Workforce Management

Конфигурируемое веб-приложение для управления внутренними техническими службами производственного предприятия: механика, электрика, энергетика, АСУ ТП, робототехника, метрология и другие инженерные подразделения.

**Репозиторий:** uzbatsu-beep/HRMS  
**План разработки:** docs/DEVELOPMENT_PLAN.md  
**Инструкции Gemini:** GEMINI.md  
**Архитектурное решение:** docs/adr/0001-modular-monolith.md  
**Прототип:** TWM_Configurable_Prototype_v0.1.html

## Назначение

TWM помогает руководителю технической службы управлять организационной структурой, компетенциями, квалификациями и допусками специалистов, сменами, доступностью, техническими заданиями и назначением исполнителей.

TWM не является системой расчёта заработной платы, SCADA или полноценной EAM/CMMS.

## Состояние проекта

Проект развивается как конфигурируемое веб-приложение (React/TypeScript,
FastAPI, PostgreSQL). Реализованы локальная авторизация, оргструктура,
персонал, матрица компетенций, проверка допусков, смены, технические
наряды и работа с бригадами. Исторический HTML-прототип сохраняется
как отдельный референс. Система всё ещё предназначена **только для
разработки и тестирования на синтетических данных**.

## Новый рабочий интерфейс (PR #12)

На рабочем экране доступна **трёхколоночная компоновка**:

- **Слева:** меню модулей; выбранный модуль открывается в центре,
  без длинной прокрутки через все остальные разделы.
- **Центр:** рабочая область выбранного модуля.
- **Справа:** список доступных предприятий, иерархия подразделений
  и поиск сотрудников, загружаемые с сервера с учётом RBAC.
  Щелчок по сотруднику открывает его карточку в модуле «Персонал».

На небольших экранах меню сворачивается, а правая панель
переносится вниз. Текущий раздел отражается в адресе как `#personnel`,
`#work` и т.д.; старый якорь `#home` по-прежнему ведёт к обзору.

Если PR #12 ещё не объединён и требуется локальный просмотр:

```powershell
git fetch origin feature/workspace-shell-navigation
git switch --track origin/feature/workspace-shell-navigation
docker compose up --build -d
```

После слияния PR достаточно `git switch main`, `git pull --ff-only`,
`docker compose up --build -d`. Откройте
`http://localhost:5173/#dashboard`. Дополнительных миграций PR #12
не требует.

Сценарии ручной приёмки и дальнейший план: `docs/UI_UX_ROADMAP.md`.


## Единый рабочий контекст (PR #14)

Выбор предприятия, подразделения и сотрудника теперь единый для интерфейса.
Правое дерево подразделений синхронизировано с центральными экранами.
Выбранный специалист сохраняется при переходе между разделами
«Персонал», «Компетенции», «Документы и допуски», «Смены и загрузка».
В «Нарядах и бригадах» выбранное подразделение используется как
предпочтительный участок при создании нового наряда.

В верхней панели доступен поиск сотрудников по **текущему предприятию**.
Он обращается к серверному API и не показывает работников за пределами
разрешённой области доступа; после выбора открывается карточка специалиста.
В заголовке экрана есть контекстная навигация, показывающая предприятие,
подразделение и выбранного сотрудника.

Состояние очищается при выходе и входе другой учётной записи.
Ни персональные данные, ни выбранные идентификаторы не сохраняются в
`localStorage` или адресе страницы. Backend остаётся единственным
источником полномочий и производственных ограничений.

Подробности и границы: `docs/adr/0010-shared-workspace-context.md`.
Сценарии проверки: `frontend/e2e/tests/05-workspace-context.spec.ts`.

## Операционный Dashboard (PR #15, объединён)

Экран `#dashboard` показывает только данные доступного предприятию и
подразделению пользователя (admin/manager/viewer с серверным RBAC): состояние
нарядов, доступность на ближайшие 15 минут, подтверждённые записи допусков,
резервирования и 30-дневную динамику. Проценты загрузки не вычисляются без
подтверждённого фонда рабочего времени. Определения и ограничения:
`docs/adr/0011-operational-analytics.md`.

## Управляемый конфигуратор (PR #16, на проверке)

В модуле «Конфигуратор» администратор создаёт версию дополнительных
информационных полей персонала (текст, целое число, флажок или список).
Схема проходит `draft → validated → approved → published`, где согласование
выполняет *другой* администратор. Дата вступления в силу задаётся при публикации
и не может быть задним числом. После публикации версия неизменяема.

Опубликованные поля появляются в карточке специалиста, доступной по RBAC.
Изменения значений выполняет администратор, и каждое сохранение создаёт
неизменяемую ревизию. Эти поля **не имеют права** подменять штатные реквизиты,
обходить проверку допусков или управлять переходами промышленных нарядов.
Миграция БД: `0010_configuration`, подробности в
`docs/adr/0012-governed-configuration.md`. Работайте только на синтетических данных.

## Автоматическая функциональная приёмка (PR #13)

В проекте есть независимый **Playwright E2E**-набор для Chromium:
проверка браузерной авторизации, меню и узкого экрана, прав доступа,
поиска персонала, назначения наряда, бригады и блокировки `on_hold`
после искусственного отзыва допуска.

Для безопасности тесты используют **отдельный Docker Compose и отдельный
том PostgreSQL**, а не базу вашей локальной рабочей версии. Синтетическое
предприятие и пользователи создаются только после установки явного флага
`E2E_ALLOW_SEED=1`; пароли передаются через переменные окружения.

Все команды для Windows, порядок изолированного запуска и просмотр
HTML-отчётов приведены в [руководстве E2E](docs/E2E_ACCEPTANCE.md).
Новая проверка запускается и в GitHub Actions, где сохраняет
скриншоты, трассировки и видео при падениях. Не используйте её на
реальном реестре сотрудников или нарядов-допусков.

## Быстрый запуск через Docker Compose

Требования:
- Docker Engine / Docker Desktop с Compose v2;
- свободные локальные порты 5173, 5432 и 8000.

1. При необходимости скопируйте .env.example в .env и измените локальные параметры.
2. Запустите:

    docker compose up --build

3. Откройте:
- Web application: http://localhost:5173
- API root: http://localhost:8000/
- Swagger / OpenAPI: http://localhost:8000/docs
- Liveness: http://localhost:8000/api/v1/health/live
- Readiness (включает PostgreSQL): http://localhost:8000/api/v1/health/ready

Остановить контейнеры: Ctrl+C, затем docker compose down. Чтобы также удалить локальный том базы данных, выполните docker compose down -v (данные будут удалены).

Учетные данные по умолчанию предназначены только для разработки. Для общей или production-среды нужны отдельные секреты, TLS, политика сетевого доступа, аутентификация и защищённое файловое хранилище.

## Локальный запуск backend без Docker

Из корня репозитория создайте виртуальное окружение и установите backend:

    python -m venv .venv
    python -m pip install -e "./backend[dev]"

Для Windows PowerShell активируйте окружение командой:

    .venv\Scripts\Activate.ps1

Установите TWM_DATABASE_URL на доступный PostgreSQL, затем:

    cd backend
    alembic upgrade head
    uvicorn app.main:app --reload

## Локальный запуск frontend

Во втором терминале:

    cd frontend
    npm install
    npm run dev

Vite проксирует /api в http://127.0.0.1:8000. Для изменения адреса задайте VITE_API_PROXY_TARGET.

## Проверки

Backend, из backend/:

    ruff check .
    pytest

Frontend, из frontend/:

    npm install
    npm run check
    npm run build

GitHub Actions выполняет backend lint, миграции и тесты на PostgreSQL, а также TypeScript check и production build frontend при Pull Request и push в main.

## Ограничения

Это foundation-сборка, а не production-система. Аутентификация, серверный RBAC, аудит, защита персональных данных, документное хранилище, предметные модули и назначение технических работ ещё не реализованы. Не вводите реальные персональные данные, юридически значимые документы и не используйте эту версию для принятия решений по промышленной безопасности.


## Phase 2 — локальная авторизация (PR #4)

После запуска `docker compose up --build` создайте первого администратора (пароль не задаётся в Git и не имеет значения по умолчанию):

```bash
docker compose exec -it backend python -m app.identity.bootstrap_admin
```

Команда запросит имя пользователя и пароль (минимум 12 символов). Она не изменяет существующего пользователя, если имя уже занято.

Затем откройте `http://localhost:5173` и войдите через панель **Доступ к системе**. Администратор может создавать локальные аккаунты с ролями `viewer`, `manager` и `admin`. Сервер защищает создание аккаунтов авторизацией и CSRF-заголовком.

API:
- `POST /api/v1/auth/login` — локальный вход; возвращает ограниченный профиль и CSRF-токен, устанавливает HttpOnly cookie.
- `GET /api/v1/auth/me` — информация о текущем входе и CSRF-токен.
- `POST /api/v1/auth/logout` — завершение и отзыв сессии (требует X-CSRF-Token).
- `GET /api/v1/auth/users` — список аккаунтов (только admin).
- `POST /api/v1/auth/users` — создание аккаунта (только admin, с CSRF).

Примените миграции `alembic upgrade head` перед запуском backend без Docker.

**Ограничения безопасности:** текущая реализация — фундамент авторизации для development. Ещё не реализованы организационные области доступа, детализированный RBAC, аудит изменений, ограничение частоты попыток входа, восстановление пароля и корпоративный SSO. Доступ в production и реальные персональные данные пока не допускаются. Подробности — `docs/adr/0002-local-identity.md`.


## Phase 2 — настройка организационной структуры (PR #5)

После применения миграций (`docker compose up --build` или `cd backend && alembic upgrade head`)
войдите учётной записью администратора и откройте на главной странице
**«Организационная структура»**.

Рекомендуемая последовательность:

1. Администратор создаёт предприятие (код и название).
2. Создаёт собственные типы подразделений, например «служба», «группа», «участок».
3. Создаёт корневые и вложенные подразделения. Глубина не фиксирована.
4. Назначает существующим пользователям с ролью manager/viewer явные разрешения
   на отдельное подразделение либо на всё поддерево.
5. Для проверки следует войти под пользователем без разрешений: все предприятия
   и подразделения будут скрыты. После назначения доступа будут видны только
   разрешённые узлы.
6. Администратор может переносить подразделение под другого родителя.
   Сервер отклоняет циклические и межпредприятийные ссылки.
7. В панели доступен журнал административных изменений.

API endpoints находятся под `/api/v1/org`; Swagger: `http://localhost:8000/docs`.

### Модель безопасности

- `admin` имеет полный доступ к структуре всех предприятий в этой установке;
- `manager` и `viewer` могут только просматривать явно разрешённые узлы;
- отсутствие грантов означает отсутствие доступа, включая список предприятий;
- для изменения структуры или разрешений требуются роль admin и CSRF-токен;
- все новые предметные API (сотрудники, квалификации, задания) **обязаны**
  отдельно использовать политику областей доступа — она не подключается автоматически.

Ограничения и архитектурные решения: `docs/adr/0003-organization-scopes.md`.
Данные всё ещё предназначены только для разработки и тестирования, без
реального персонала и производственных допусков.


## Phase 3 — технический персонал (PR #6)

В **«Технический персонал»** после авторизации доступны реальные карточки
специалистов, сохраняемые в PostgreSQL. Администратор может:

- создать карточку с табельным кодом, ФИО, подразделением, должностью и датой назначения;
- изменить ФИО, зарегистрировать перевод с указанием даты, назначить дополнительную
  бригаду и архивировать карточку без удаления истории;
- просмотреть журнал изменений через `GET /api/v1/personnel/audit`;
- назначить менеджеру/наблюдателю доступ к подразделению через раздел Organization.

**Manager/Viewer:** видят только тех специалистов, чьё **действующее основное
подразделение** входит в их разрешённые области доступа. Участие специалиста в
дополнительной бригаде не раскрывает всю его карточку. Старые назначения в
подразделениях вне области доступа скрыты из истории. Создавать и изменять
карточки без роли admin нельзя.

**API:** `/api/v1/personnel`. Swagger: `http://localhost:8000/docs`.
Применяйте миграции `alembic upgrade head` перед локальным запуском API.

Изоляция предприятий, временные ограничения, технические предположения и
отложенные функции описаны в `docs/adr/0004-personnel.md`.
Не используйте текущую dev-версию с реальными персональными данными.


## Phase 4 — Competence Management (PR #7)

Раздел **«Компетенции и квалификационная матрица»** работает через PostgreSQL,
FastAPI и авторизованные запросы. После применения миграции
`0005_competence` доступны следующие шаги:

1. Администратор создаёт категории компетенций (с вложенными подкатегориями).
2. Публикует шкалу оценки: код, версия и от 2 до 10 описанных уровней.
   **Опубликованная версия неизменяема.** Изменения создаются как новая версия
   под тем же кодом; существующие навыки продолжают ссылаться на старую.
3. Создаёт навык, связав его с категорией и конкретной версией шкалы.
4. Для самооценки связывает UserAccount с Person (по одному аккаунту на Person).
   Связанный сотрудник может подавать самооценки без организационных прав на
   других работников.
5. Уполномоченный manager (в своей области доступа) либо admin может создавать
   экспертные предложения, подтверждать или отклонять оценки **другого автора**.
   Утверждение требует записи о подтверждающем материале и обоснования.
6. Только утверждённые оценки отображаются в матрице: по каждой паре
   «сотрудник–навык» берётся последнее подтверждение, остальные предложения
   сохраняются в истории.

**API:** `/api/v1/competence` (подробная схема: `http://localhost:8000/docs`).

**Ограничения:** ссылки/описания доказательств пока являются **метаданными**, а
не загруженными или проверенными документами; юридические допуски и
сертификация здесь не реализованы. Нельзя использовать эту матрицу как
подтверждение допуска к опасной работе. До внедрения защиты персональных
данных, production-аутентификации и системы проверки документов работайте
только с демонстрационными данными.

Архитектурные правила: `docs/adr/0005-competence.md`.


## Phase 5 — Credentials Management (PR #8)

После применения `alembic upgrade head` (миграция `0006_credentials`)
в интерфейсе **«Квалификации, сертификаты и допуски»** можно:

1. Создать тип документа — `permit`, `certificate`, `qualification`,
   `training`. Для документов, критичных для безопасности,
   **дата окончания обязательна**.
2. Настроить список обязательных документов для кода вида работ
   (например, `robot-maintenance`, `electrical-work`).
   Несколько требований одного кода объединяются логическим **И**.
3. Зарегистрировать документ выбранного сотрудника: номер, организация,
   дата выдачи, начало и окончание действия. Новая запись имеет статус
   `pending`, то есть сама по себе не даёт допуска.
4. Независимый проверяющий (другой admin либо manager с правом просмотра
   сотрудника) может отметить запись `verified` или `rejected`
   с обязательным обоснованием.
5. Администратор может отозвать проверенный документ с указанием причины.
   Повторно утвердить отозванную запись нельзя — требуется новая запись.
6. Запустить проверку по сотруднику, коду операции и конкретной дате:
   сервис покажет результат и **причины блокировки**.
   Когда требования не настроены, результат всегда отрицательный.

**Роли:** admin управляет документами и правилами; manager с назначенной
областью доступа может просматривать и независимо проверять документы;
viewer имеет только просмотр доступных данных. Пользователь, связанный с
собственной карточкой, может видеть свои документы без доступа к чужим.

**API:** `/api/v1/credentials`, Swagger `http://localhost:8000/docs`.

**Важное ограничение:** документы представлены только учётными метаданными;
физическая проверка подлинности и безопасное хранение вложений пока не
внедрены. Успешный результат API — это прохождение настроенных требований,
**а не юридическое разрешение на проведение опасных работ**.
Предметный модуль Work Management должен будет проверять все обязательные
допуски при непосредственном назначении исполнителя.

Текущая версия предназначена исключительно для разработки и синтетических
данных. Подробно: `docs/adr/0006-credentials-safety.md`.


## Phase 6 — Availability & Scheduling (PR #9)

После применения `alembic upgrade head` (миграция `0007_availability`)
в интерфейсе **«Смены, доступность и загрузка»** администратор может:

1. Настроить на конкретного специалиста еженедельную смену: день недели,
   местное время начала и окончания, часовой пояс IANA, диапазон дат
   действия. Если конец раньше начала, смена ночная и заканчивается
   на следующие сутки.
2. Добавить нерабочий день предприятия с датой и часовым поясом.
3. Зарегистрировать отсутствие (`leave`, `training`, `unavailable`)
   или отменить его, сохранив историю.
4. Проверить потенциальную доступность специалиста на интервал до 24 часов.
   Вне смены, при отсутствии, в нерабочий день, при уже занятом времени
   или без организационного назначения результат будет **отрицательным**.
5. Забронировать время. Сервер проверяет доступность **после блокировки
   предприятия в транзакции PostgreSQL**, чтобы два параллельных запроса
   через API не могли одновременно забронировать один интервал.
6. Отменить бронь либо отключить правило смены без удаления истории.
7. Просмотреть планово занятые минуты, число активных бронирований и
   длительность отсутствий за выбранный период.

**Временная модель:** интервалы задаются с явным UTC-смещением,
хранятся в UTC и имеют границы `[start, end)`, то есть соседние события
не пересекаются. Поля ввода периодов в React намеренно подписаны **UTC**;
локальное время смены вводится отдельно с часовым поясом IANA.
При неоднозначной дате/времени на переходе DST смена не считается
валидным покрытием для проверки.

Менеджеры и наблюдатели имеют просмотр только назначенных им
организационных областей; категорию/комментарий отсутствия и внешние
коды бронирований они не получают. Привязанный к аккаунту сотрудник
может открыть собственный календарь.

**API:** `/api/v1/availability`; Swagger `http://localhost:8000/docs`.

**Граница безопасности:** бронь не является нарядом на работу. Реальная
допустимость исполнителя должна позже одновременно учитывать компетенции,
действующие производственные допуски и календарную доступность.
Нерабочие дни, введённые после брони, могут её инвалидировать — текущая
версия сообщает это при новой проверке, но не выполняет автоматический
перенос. Учёт загрузки не предназначен для расчёта рабочего времени
или оплаты труда.

Архитектура и ограничения: `docs/adr/0007-availability-scheduling.md`.
Только синтетические данные в среде разработки.


## Phase 7 — Work Management (PR #10)

После применения `alembic upgrade head` (миграция
`0008_work_management`) в разделе **«Технические задания и назначение
специалистов»** можно создать наряд на техническую операцию, выбрать
подразделение, дату/время, код вида работ и от 1 до 20 компетенций с
обязательным минимальным подтверждённым уровнем.

### Рабочий сценарий

1. Настройте организационную структуру, специалистов и актуальные основные
   назначения в подразделения.
2. Создайте категории, шкалы, навыки, подтвердите компетенции сотрудников
   независимым рецензентом (PR #7).
3. Настройте обязательные типы допуска для `activity_code`, внесите и
   подтвердите документы с датами действия (PR #8).
4. Создайте недельные смены и проверьте отсутствия, нерабочие дни,
   занятость ресурса (PR #9).
5. Создайте WorkOrder с фиксированными требованиями и окном до 24 часов.
   В интерфейсе появится список кандидатов из нужного подразделения.
6. Просмотрите причины отказов по **компетенциям, допускам, графику и
   организационной принадлежности**. Только при полном прохождении проверок
   можно назначить исполнителя. Сервер повторно проверяет всё под блокировкой
   предприятия, затем в одной транзакции создаёт запись о назначении
   и бронирование времени. Нельзя назначить второго исполнителя на тот же наряд.
7. В начале планового интервала используйте **«Начать с повторной проверкой»**.
   Проверки выполняются снова, исключая из конфликтов только собственную бронь:
   отозванный документ или новое отсутствие не даст начать работу.
8. Наряд можно завершить или отменить. Отмена освобождает бронь и сохраняет
   историю принятых решений.

**Роли:** `admin` — все операции; `manager` — только наряды и специалисты
разрешённых ему подразделений; `viewer` — просмотр в своей области доступа.

**API:** `/api/v1/work`, OpenAPI: `http://localhost:8000/docs`.
Архитектура, предикаты и ограничения: `docs/adr/0008-work-management.md`.

**Граница безопасности:** назначение/бронь в этом приложении **не являются
юридическим разрешением на опасную работу**. Не реализованы формальные
наряды-допуски, LOTO, привязка допуска к машине, контроль СИЗ и условий
рабочего места. Результаты считаются только по введённым данным, статусам
проверки и настроенным правилам. После начала работы нет автоматического
аварийного прекращения при отзыве допуска. Не используйте PR #10 для
реального допуска к опасным работам или личных производственных данных:
это **development/test prototype**.


## Phase 8 — Work Crews & Safety Revalidation (PR #11)

После `alembic upgrade head` (миграция `0009_work_execution`)
модуль **Work Management** поддерживает бригады на базе одного наряда.

1. При создании задайте приоритет: `routine` (плановый),
   `normal` (обычный), `urgent` (срочный) или `critical`
   (критический). Приоритет можно изменить только до начала работ,
   указав обоснование. Повышенный приоритет **не отменяет допуски**.
2. Назначьте ответственного, как в PR #10. Затем добавьте до восьми
   участников в ролях `specialist`, `assistant` или `observer`.
   **Каждый участник**, в том числе наблюдатель, проходит все обязательные
   серверные проверки; каждому выделяется собственная бронь рабочего времени.
3. Перед началом работ можно исключить участника с объяснением причины,
   освободив его бронь. Повторное добавление ранее исключённого сотрудника
   в тот же наряд текущая модель не допускает: история сохраняется.
4. Ответственного до начала выполнения можно заменить. Сервер проверяет
   замену и атомарно освобождает прежний интервал, резервирует новый и
   фиксирует операцию в аудите.
5. **Старт требует валидности всей бригады**, а не только ответственного.
   Сроки документов, компетенции, принадлежность подразделению, графики,
   отсутствие и активность всех отдельных броней проверяются повторно.
6. После начала доступны ручная диагностическая проверка `GET /safety` и
   фиксируемая повторная проверка `POST /revalidate`. Если у сотрудника
   отозван допуск или время занято, наряд становится `on_hold` и
   дальнейшее завершение в приложении блокируется.
7. Руководитель может вручную приостановить работу в HRMS, зафиксировав
   причину. Возобновить её можно только **внутри запланированного окна**,
   после повторного успешного прохождения всех проверок и записи
   обоснования решения.
8. При отмене наряда брони всех действующих участников освобождаются.
   При завершении проверка бригады также повторяется.

**Ограничение:** `on_hold` — только состояние программного документооборота.
Это не аварийный останов оборудования, PLC-интерлок, электронный наряд-допуск
или непрерывный контроль статуса удостоверений. Автоматического мониторинга
позднего отзыва документа **нет**: нарушение выявляется при явной проверке
или попытке завершения. Фактическую безопасность обеспечивают
производственные процедуры, допуск ответственного лица и местные регламенты.

Подробности: `docs/adr/0009-work-crews-and-safety-holds.md`.
Среда предназначена только для разработки и синтетических записей.


## PR #17 — Реестр оборудования и разрешения на работы (на проверке)

Реестр оборудования — `#equipment`, а привязка актива и разрешения — в
карточке наряда `#work`. Для нарядов, связанных с оборудованием, сервер
проверяет наличие **одобренного другим администратором** разрешения, актуальный
статус актива и персональные дополнительные допуски при проверках назначения,
запуска, возобновления и повторной проверки safety.

Дополнительные сведения, неполный электронный контроль опасностей, ограничения
и последовательность действий описаны в
`docs/adr/0013-equipment-permit-workflow.md`.
Миграция: `0011_equipment_permits`.

**Критично:** это регистрация человеческих утверждений, а не аппаратная
блокировка оборудования, проверка LOTO или юридически действительный наряд-допуск.
Запрещено использовать прототип для реальных опасных работ.

## PR #18 — Специфические навыки оборудования и сводка готовности (на проверке)

Администратор добавляет к оборудованию дополнительные обязательные технические
навыки и минимальные утверждённые уровни в реестре `#equipment`.
Требования не заменяют компетенции и допуски наряда; они суммируются с ними
на уровне backend. Изменение во время выполнения работы автоматически задаёт
статус `on_hold` в HRMS, но не останавливает машину.

Новая сводка /readiness показывает состояния разрешений и активов для нарядов
с учётом подразделений и RBAC, **не утверждает**, что экипаж допущен и не
выполняет проверку физического состояния рабочего места. Подробнее:
`docs/adr/0014-equipment-skill-readiness.md`.
Миграция БД: `0012_asset_skill_gates`.
Используйте только синтетические тестовые данные.


## PR #19 — Окна обслуживания оборудования (на проверке)

В реестре #equipment можно зарегистрировать плановое окно недоступности
станка/робота: начало, конец и обоснование, а также отменить окно с сохранением
полной истории. Новые окна, пересекающие уже запланированное обслуживание,
отклоняются. Проверки подбора персонала и разрешений для *связанного*
наряда блокируют пересечение его планового периода с окном обслуживания.
Если окно появляется во время выполнения пересекающейся работы, HRMS
переводит наряд в программный статус on_hold. Отмена окна не возобновляет
наряд автоматически.

Миграция 0013_asset_downtime; ADR-0015. Физический останов, LOTO,
сигналы с ПЛК, фактическое состояние оборудования и юридический допуск
здесь **не** реализованы. Только синтетические данные в тестовом окружении.


## PR #20 — Проверка бригады из сводки оборудования (на проверке)

В разделе #equipment роли Admin и Manager могут вручную запросить
**моментальный снимок программной готовности бригады** отдельного наряда.
Сервер повторно оценивает назначенные компетенции, документы, календарные
бронирования, требования конкретного актива и разрешение на работы. Ответ
содержит только время проверки, агрегированные показатели и коды проблем:
ФИО, идентификаторы работников и данные документов не передаются.

Проверка доступна лишь при доступе к подразделениям **и наряда, и актива**.
Это GET без записи в журнал/изменения статуса: не заменяет фактическое действие
«Повторно проверить» в карточке наряда и не разрешает физический запуск
оборудования. Документация: docs/adr/0016-crew-readiness-snapshot.md.
