# Как внести изменение в TWM

Для локального запуска, создания администратора и запуска тестов используйте [руководство разработчика](docs/DEVELOPMENT.md) и [индекс документации](docs/DOCUMENTATION_INDEX.md). Перед работой проверьте [реализованные возможности](docs/IMPLEMENTATION_STATUS.md) и открытые PR.

## Сообщить об ошибке или предложить функцию

В [Issues](https://github.com/uzbatsu-beep/HRMS/issues/new/choose) выберите шаблон. Для ошибки укажите коммит, модуль, роль, область доступа, шаги на вымышленных данных и ожидаемый результат. Для новой функции опишите задачу сотрудника техслужбы и наблюдаемый критерий приёмки. Потенциальное раскрытие персональных данных или нарушение прав доступа передавайте по [политике безопасности](SECURITY.md).

## Подготовить pull request

1. Обновите локальный `main` и создайте ветку `feature/...`, `fix/...` или `docs/...`.
2. Для изменения бизнес-правила найдите действующий [ADR](docs/adr/) и соответствующий тест. Например, для назначения бригады проверьте как успешное назначение, так и отказ при отозванном допуске.
3. Изменение схемы БД сопровождайте миграцией Alembic. Проверяйте обновление существующих данных и опишите ограничения отката.
4. Запустите проверки затронутых компонентов. Обновите документацию, если меняются сценарий, API, способ запуска или ограничения.
5. Откройте PR в `main`. Опишите сценарий до и после изменения, проверки и их результат. Для интерфейса приложите снимок с синтетическими данными. Дождитесь CI и решения сопровождающего о слиянии.

Условия участия изложены в [кодексе поведения](CODE_OF_CONDUCT.md). Проект распространяется по [GNU GPL версии 3](LICENSE) (`GPL-3.0-only`). Включая сторонний код, укажите его источник и условия использования.

## Качество документации и ограничения пилота

- Сначала сверяйте `main`, открытые Draft PR, Actions run и [G6](docs/PILOT_READINESS_G6.md); не переносите заявления из исторических ADR в «текущий статус» без проверки.
- Изменение Markdown должно сохранять рабочие относительные ссылки; при новом PR выполняйте `python scripts/check_docs.py` (также запускается в обязательном CI).
- При корректировке API/permissions приложите отрицательные тесты tenant/unit/operation, обновите миграцию и матрицу требований. При работе с `personnel`/допусками — проверьте, что в Issue, screenshot и отчёте нет настоящих ПДн.
- На 2026-11-21 `main` защищена Ruleset #27708090 и пятью required CI jobs. PR #39/#38/#36 включены в `main`; реальные ПДн и pilot остаются NO-GO.
