# TWM — план приёмки и контрольные сценарии

**Версия:** 0.3 · **Дата:** 2026-11-19 · **Среда:** изолированная PostgreSQL 16, вымышленные сотрудники и оборудование.

Документ определяет *ожидаемые критерии* для регрессионной и пред-пилотной приёмки. Ссылки на существующие наборы тестов не означают, что каждый сценарий ниже уже автоматизирован. Фактические результаты записывать в PR/протоколе.

## 1. Виды проверок

1. **Backend:** `cd backend && ruff check . && pytest`, миграции `alembic upgrade head` на PostgreSQL.
2. **Frontend:** `cd frontend && npm ci && npm run check && npm run test:e2e:check && npm run build`.
3. **Full-stack E2E:** `npm run test:e2e` только на отдельном тестовом окружении по [E2E_ACCEPTANCE](E2E_ACCEPTANCE.md); не использовать `E2E_ALLOW_SEED=1` на рабочих данных.
4. **Ручная UX-приёмка:** desktop, узкий экран, клавиатурная навигация, пустые/ошибочные состояния, локализация дат.
5. **Pilot gate:** отдельный протокол восстановления, контроля доступа к ПДн, инфраструктуры и согласования владельцем.

## 3. Gate по этапам

| Gate | Обязательные сценарии | Доказательства |
|---|---|---|
| G0 — план | Сверка всех файлов и ссылок; `main` не изменён | PR diff и review владельца |
| G1 — безопасность | AC-01..05, AC-10..14 | Негативные API-тесты, CI и threat-model update |
| G2 — интерфейс | AC-17,18 + ручная навигация admin/manager/viewer | Playwright, скриншоты/отчёт без ПДн |
| G3 — права work | AC-01..03, 07,10,11,13 | Отказ при устаревших разрешениях, запрет обхода backend |
| G4 — matching и race | AC-04..09,15,16 | PostgreSQL parallel tests и E2E с >100 кандидатами |
| G5 — configurator | AC-12,22 + регрессия AC-04..11 | Версионирование, review, audit, повторная проверка |
| G6 — пилот | AC-01..22 применимые, 19–21 обязательно по объёму | Протокол DR/PII/TLS/secrets + письменное решение владельца |

## 4. Форма записи о фактическом испытании

Заполнить в каждом PR / протоколе: **commit SHA**, дата, тестовое окружение, версии PostgreSQL/Python/Node, выполненная команда, результат (PASS/FAIL/SKIP с обоснованием), ссылка на job/artifact, инициатор проверки, дефект/Issue и остаточный риск.

Для каждой миграции: старый/new head, отдельная новая БД, повторный прогон, невозможный/опасный downgrade отдельно обозначить. Никогда не выполнять разрушительные тесты на действующей БД.

**Запрет ложной интерпретации:** успешный software gate не является физическим/юридическим допуском к работам. Аппаратный interlock, LOTO, лицензированные PTW и ответственные лица находятся вне TWM.
