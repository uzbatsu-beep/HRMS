# TWM G6 — руководство резервного копирования и восстановления PostgreSQL

**Применение:** только тестовая/изолированная инфраструктура до утверждения пилота.
**Приоритет:** P0. Резервная копия считается пригодной только после успешного restore drill.
**Штатный dev Compose не является production-контуром.**

## Что создаётся

`ops/postgres_dr.py` вызывает штатный PostgreSQL 16 `pg_dump -Fc` и
`pg_restore`. Архив включает схему и данные указанной БД. Рядом сохраняется
`*.dump.manifest.json` с SHA-256, размером, временем и версией Alembic.
Скрипт не записывает пользовательские данные в manifest и не показывает
строки подключения в stdout. `pg_dump` не копирует настройки/роли кластера
и не заменяет WAL/PITR.

Использовать файл и manifest как **единый комплект**; хранить вне сервера БД
с шифрованием, раздельными доступами, контролем целостности и запретом
изменения/удаления для операционного аккаунта. Ротация, retention и
географически разнесённые копии должны быть утверждены до пилота.

## Предварительные требования

- Версия **клиента pg_dump/pg_restore 16** для сервера PostgreSQL 16.
- Права для чтения всех необходимых схем; отдельные полномочия на создание
  **тестовой** базы для восстановления. Не применять резервные credentials
  сервисного runtime-аккаунта там, где можно использовать отдельную роль.
- `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSFILE`; последний —
  файл libpq passfile с доступом **только владельцу** (0600 в Linux).
  Не использовать `PGPASSWORD` — скрипт откажет в запуске.
- В удалённом production-контуре установить `PGSSLMODE=verify-full`,
  корректный `PGSSLROOTCERT` и подтверждённый серверный сертификат.
- Отдельная временная директория и достаточное свободное место.

Не хранить настоящие passfiles, дампы и сертификаты в Git, артефактах CI,
общих сетевых папках, открытых логах или в тикетах.

## 1. Снятие копии

После задания переменных окружения через защищённую оболочку/secret manager:

```sh
umask 077
python3 ops/postgres_dr.py backup --out /private/backups/twm-20261120.dump
```

Файл должен быть новым (существующий не перезаписывается). Передача в
шифрованное офлайн/off-site хранилище выполняется **отдельно** и должна быть
подтверждена журналом backup, объектом/версией и проверкой checksum.
Сохранить Alembic revision и SHA-256 из manifest в протокол.

## 2. Проверка восстановления, только новая БД

Используйте другое изолированное тестовое окружение PostgreSQL, не подключённое
к приложению и реальным сотрудникам. Определите и зафиксируйте допустимые
RPO и RTO с владельцем — **пока не утверждены**.

```sh
export TWM_RESTORE_ALLOW=1
python3 ops/postgres_dr.py restore \
  --file /private/backups/twm-20261120.dump \
  --target-db twm_restore_drill20261120
```

Скрипт проверяет SHA-256/размер, архив, создаёт только базу с именем
`twm_restore_...`, запускает `pg_restore --single-transaction --exit-on-error`
и сверяет `alembic_version`. **Никогда не выполняет DROP DATABASE** и не
перезаписывает существующую базу. При ошибке оставляет целевую базу для
разбора; очищать только отдельным ручным решением.

Проверить вручную (с вымышленными данными):
- контроль количества сотрудников, сотрудников подразделений, нарядов и
  выданных допусков в источнике и восстановленной копии;
- ссылки FK, историю событий и состояние последних миграций;
- запуск API с **другими** одноразовыми секретами и тестовый вход;
- тест блокировки заведомо недопустимого назначения; повторный отзыв сессии;
- фактическую длительность и целостность данных, после чего оформить
  протокол: дата, команда, версия клиента, checksum, RPO/RTO, исполнитель.

## 3. Изменения схемы и аварийный откат

Перед любой миграцией получить непрерывную копию БД и протестировать
восстановление **точно того** архива. Alembic downgrade может удалять
данные и не является безопасным резервным планом. Rollback приложения
выполнять только по согласованной матрице совместимости схем; в противном
случае восстанавливать БД из проверенного архива в новом окружении и
согласовывать окно остановки.

## 4. Полноценный DR перед пилотом (не реализовано здесь)

Нужно дополнительно разработать и подтвердить: политику хранения и удаления,
восстановление PostgreSQL roles/grants (pg_dump их не сохраняет),
инкрементальное архивирование WAL/PITR, off-site/immutable storage,
сквозное шифрование ключами вне БД, расписание и оповещение о неудаче,
тест восстановления **полного** синтетического набора через API и
подписанный результат по RPO/RTO. Текущий smoke-test CI проверяет
основной механизм, но **не доказывает** выполнение этих условий.
