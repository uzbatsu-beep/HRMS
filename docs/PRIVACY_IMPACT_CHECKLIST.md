# TWM G6 — проект оценки обработки персональных данных (PIA)

**Статус:** DRAFT / NO-GO для реального персонала. Владелец обработки, юрист,
специалист ИБ и представители подразделений должны согласовать каждую строку.
Правовая база и юрисдикция организации **не определены**, нельзя предполагать
применимость одного закона для всех предприятий.

## 1. Инвентаризация

| Категория | Реальные данные в текущей модели | Риск/ограничение |
|---|---|---|
| Профиль | ФИО, табельный код, должность, подразделение, история переводов | Идентифицируемые персональные сведения |
| Компетенции | уровень, даты оценки, проверяющий, комментарии | Индивидуальные сведения о профессиональной квалификации |
| Допуски | номер/ссылка документа, выдавший орган, срок, отзыв, пояснения | Чувствительные профессиональные сведения и история проверок |
| Доступность | смены, отпуска/обучение/отсутствие, бронирование | Профиль присутствия и занятости; не добавлять медицинские причины |
| Наряды | задания, назначения, история действий, заметки и причины | Профиль трудовой активности, потенциальная дисциплинарная трактовка |
| Configurator v1/v2 | текстовые пользовательские поля/ответы, статусы и free-text заметки | Потребитель может ввести лишние ПДн; ограничения схемы не обеспечивают PII-политику |
| Identity | username, сессии и токены (в БД хэши), ACL/grants | Данные доступа; защищать от экспорта/логирования |
| Аудит | ID субъектов и авторов, временные отметки, details_json, комментарии | Совокупность позволяет повторную идентификацию |
| E2E/логи/скриншоты | снимки экранов, test results, error traces | Только синтетические значения; не прикладывать снимки реальных карточек |
| Архивы и копии | полный дамп БД с вышеуказанными сведениями | Максимальная чувствительность; шифрование и ограничение доступа |

## 2. Минимальные решения владельца до любых реальных записей

1. Для каждого поля: назначение/цель, источник истины, правовое основание,
   обязательность, получатели, перечень ролей, экспорт, аудит чтения,
   срок хранения, удаление/обезличивание и исключения по трудовому/архивному праву.
2. Заключить/утвердить правила доступа admin/manager/viewer и дополнительные
   exact-unit grants. Проверить необходимость *field-level visibility*:
   существующий unit-RBAC **не обеспечивает автоматически** сокрытие
   отдельных реквизитов документов и произвольного текста.
3. Запретить в произвольных полях медицинские данные, паспортные номера,
   пароли, секреты, сведения о политических/религиозных убеждениях и иные
   неразрешённые категории до отдельного формального решения.
4. Для логов: исключить cookie, CSRF, пароли, текст документа, свободные
   заметки, тело HTTP-запроса/ответа. В пилотном Nginx access log выключен,
   в Uvicorn выключен access log — но **не выполнен** аудит всех
   обработчиков ошибок и сторонних компонентов.
5. Отдельно утвердить retention для audit events, login sessions, архивов,
   отозванных допусков, пользовательских полей, а также поэтапное
   обезличивание и безопасное удаление всех копий.
6. Согласовать уведомление работников, запрос доступа/исправления,
   реакцию на инциденты, назначить администратора ПДн и журнал доступа к БД.
7. Отработать удаление/отзыв доступа, экспорт ПДн и сценарии утери
   резервной копии **только на вымышленных данных**.

## 3. Отрицательные тесты и evidence

- API: роль viewer не получает чужое enterprise/unit; профиль, выдача допусков,
  отчёты, конфигуратор и audit endpoint проверяются по отдельности.
- Различия в ошибках 403/404 не дают искать скрытые объекты.
- Администратор и проверяющий не утверждают собственные заявления;
  перевод и отзыв grant действуют немедленно.
- В журнале приложения и артефактах CI нет cookie, текстов заметок, паролей,
  номеров документов и реальных ФИО.
- Формы с нестандартными полями не обходят маскирование/retention.
- Результаты: матрица ACL с ID тестов, отчёт ИБ и юридическое заключение.

**Известный разрыв:** в текущих API есть `details_json`, `review_note`,
`document_reference` и пользовательский свободный текст. Автоматически
считать их безопасными для всех администраторов или логов нельзя. Поле
`PersonDetail` раскрывает историю переводов; необходимо принять политику
и проверить дифференциальные права на просмотр.

До закрытия этих пунктов: **NO-GO, только синтетические данные**.

## 4. PR #36 — технический кандидат на закрытие части OPS-05

В отдельной ветке предложены metadata-only события чтения `personal_data_read_events`, маскирование `CredentialView` для пользователей без отдельного `credentials.record.read_sensitive`, сокрытие свободного текста доказательств от обычного viewer, redaction новых аудитов изменений ФИО и причин отзыва, no-store ответов. **Это частичный контроль, не готовая PIA.**

Исторические audit-строки с исходными значениями остаются в БД (API скрывает отдельные legacy поля). Не выполнять их удаление/перезапись до юридического retention review; доступ администраторов и прямой SQL-доступ нужно разграничить. Аудит чтения покрывает только перечисленные в [PR36_SECURITY_PRIVACY.md](PR36_SECURITY_PRIVACY.md) маршруты, не автоматически все производные отчёты, service cases и exports. До подписанного разрешения — только синтетические данные.
