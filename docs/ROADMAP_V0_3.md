## 1. Продуктовая цель и границы

TWM (Technical Workforce Management) — конфигурируемая система для руководителей и специалистов технических служб промышленного предприятия (АСУ ТП, КИПиА, электрика, механика, робототехника, энергетика, метрология). Система связывает подразделение и специалиста, подтверждённую компетенцию, документ/допуск, смену и доступность, технический наряд, требования конкретного оборудования и объяснимое назначение бригады.

**Не является:** системой расчёта зарплаты, SCADA, промышленной системой безопасности, сертифицированной Permit-to-Work/LOTO или полной CMMS/EAM. «Допущен приложением» **не равно** «разрешено приступать к опасной работе». Фактический допуск и останов оборудования регулируются процедурами и техническими средствами предприятия.

### Неизменяемые ограничения продукта

1. Backend — единственный источник истины для полномочий, квалификации, допусков, доступности, назначения и запуска наряда. UI, ML/AI и приоритет задания не могут обходить блокирующие проверки.
2. Tenant/enterprise и organizational-unit scope применяются на сервере; отсутствие явных полномочий означает отказ.
3. Согласование критичных решений — независимо от автора; история изменений, публикаций и отзыва сохраняется.
4. Назначение человека и резервирование его времени — согласованная транзакция с повторной проверкой.
5. Безопасность при физической работе обеспечивают внешние утверждённые процедуры/системы. TWM не управляет ПЛК, роботами или interlock.
6. Новые проверки выполняются на изолированных вымышленных данных; CI не должен использовать реальную БД предприятия.

## 2. Подтверждённый baseline

| Область | Наличие в main | Ограничение |
|---|---|---|
| Backend/Frontend/БД | FastAPI + SQLAlchemy + Alembic + PostgreSQL; React/TypeScript/Vite; Compose | Compose — dev, не production-манифест |
| Identity | Локальные аккаунты, Argon2id, 8-часовые отзывные сессии, cookie+CSRF | Нет отдельного production IAM, rate limiting и SSO |
| Organization/Personnel | Дерево подразделений, scope-RBAC, история переводов, карточки | Не завершена детальная политика персональных полей и импорта |
| Competence/Credentials | Каталоги, опубликованные шкалы, независимые решения, срок действия/отзыв, hard gates | Подтверждения — метаданные; не проверенные оригиналы документов |
| Availability/Work | Смены и DST, отсутствия, резервирования, подбор и бригады, приоритет, on_hold | Кандидаты ограничены первыми 100 до проверки |
| Equipment | Активы, связанные наряды, требования, разрешения, простои, версии правил и аудит | Не сертифицированный PTW; нет автоматического физического останова |
| Analytics | RBAC-ограниченные KPI, 30 дней, состояние ресурсов | Не вычислять «утилизацию» без фонда времени |
| Configurator | Версионные дополнительные поля Person с независимым утверждением | Нет универсального конструктора workflow и сущностей |
| Authorization | Три базовые роли и пять делегированных operation grants по конкретным unit | Не полноценный динамический RBAC для всех операций |
| Качество | CI: backend, frontend, Playwright; миграции PostgreSQL; 21 ADR | Нет подтверждения production-нагрузки и disaster recovery |

Подтверждение baseline: [статус](IMPLEMENTATION_STATUS.md), [ADR](adr/), [последний успешный CI](https://github.com/uzbatsu-beep/HRMS/actions/runs/44280041886). На коммите после PR #25 задокументированы 116 pytest и 24 Playwright; не переносить эти числа на новые коммиты без проверки журналов.

### Definition of Done для любого функционального PR

1. Проблема, пользовательский сценарий, исключения и критерии приёмки описаны до реализации.
2. Сервер проверяет enterprise/unit/operation и все применимые hard gates на **каждом** критичном переходе.
3. Миграция обратимо и воспроизводимо применяется на чистой тестовой PostgreSQL; отдельно разобраны необратимые downgrade.
4. Негативные тесты tenant isolation, CSRF, разрешений, просроченных/отозванных допусков и конкурентных действий добавлены, где они относятся к изменению.
5. `ruff check .`, `pytest`, `npm ci`, `npm run check`, `npm run build`, `npm run test:e2e` проходят в применимой среде CI. Ссылки на запуск приложены к PR.
6. Обновлены README/ADR/матрица требований и Playwright-сценарии для пользовательских изменений.
7. Изменения выполнены в отдельной ветке; PR не объединяется без согласования владельца.

## 6. Отдельные продуктовые решения перед расширением

Нужно зафиксировать до реализации G5/G7: единица конфигурации (предприятие/площадка); модель статусов/переходов и допустимые полномочия; политика ПДн и сроки хранения; канонические источники данных сотрудников, активов и задач; производство on-premises или private cloud; SSO/OIDC; стратегия версионированных интеграций. Без согласования этих решений не зашивать предположения в бизнес-правила.

## 7. Зависимости и точки контроля

- G1 → безопасная архитектурная база для последующих RBAC/конфигурируемых маршрутов.
- G2 и G3 могут развиваться параллельно после уточнения API, но UX не служит заменой authorization checks.
- G4 обязательно до масштабных пилотных списков (более 100 сотрудников в unit).
- G5 только после формализованного набора неизменяемых правил (список в §1).
- G6 является **блокирующим** для перевода любых реальных данных и доступа не-тестовых пользователей.
- Новое решение фиксируется ADR, а статус матрицы меняется только после merged PR и проверяемого evidence.
