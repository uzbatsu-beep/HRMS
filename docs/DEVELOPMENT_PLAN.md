# TWM — план дальнейшей разработки

**Проект:** Technical Workforce Management  
**Репозиторий:** `uzbatsu-beep/HRMS`  
**Версия плана:** 0.2  
**Дата фиксации:** 2026-11-12  
**Статус:** предложенный план; решения, отмеченные как открытые, требуют подтверждения.

## 1. Резюме и исходное состояние

Цель проекта — собственное конфигурируемое веб-приложение для управления внутренними техническими службами производственного предприятия: механика, электрика, энергетика, АСУ ТП, робототехника, метрология и другие инженерные подразделения.

Это не payroll-система и не полноценная EAM/CMMS. Основной пользовательский результат — понимание того, **кто, какими подтверждёнными компетенциями и допусками обладает, когда доступен, какие технические работы может выполнять и почему система рекомендует именно этого исполнителя**.

### Состояние репозитория на дату плана

Проверена ветка `main`:

- `TWM_Configurable_Prototype_v0.1.html` — интерактивный одностраничный frontend-прототип;
- `README .md` — подробное описание текущего прототипа (имя файла содержит пробел);
- `README.md` — краткий заголовок без полноценного описания;
- одна ветка `main`;
- открытых Issues и Pull Requests на момент проверки нет;
- серверного backend, PostgreSQL, миграций, CI и автоматических тестов в репозитории пока нет;
- `main` на момент проверки не защищена правилами ветки.

Прототип — полезный визуальный и сценарный baseline. Его следует сохранить и использовать как референс при переносе функций в новое приложение. Не переписывать его вслепую и не считать его production-реализацией.

## 2. Продуктовые границы

### Входит в целевой продукт

1. Настраиваемая организационная структура предприятия, площадок, служб, подразделений, бригад и должностей.
2. Профили сотрудников и назначаемых трудовых ресурсов.
3. Каталог технических специальностей и иерархическая матрица компетенций.
4. Настраиваемые шкалы оценки навыков и история подтверждения оценок.
5. Квалификации, сертификаты, аттестации, допуски, сроки действия и область применимости.
6. Рабочие календари, смены, доступность и загрузка.
7. Заявки, технические задания, операции и требования к исполнителям.
8. Объяснимый подбор исполнителей и назначение на работы.
9. Учёт плановых и фактических трудозатрат.
10. Аналитика квалификационного покрытия, дефицита компетенций, загрузки и рисков.
11. Конфигуратор справочников, шкал, ролей, части форм и рабочих правил.
12. API и интеграция с внешней HRMS/ERP/CMMS/EAM в последующих этапах.

### Не входит в первый MVP

- расчёт заработной платы и полное кадровое делопроизводство;
- полноценная EAM/CMMS и управление всем жизненным циклом активов;
- прямое управление PLC, роботами, приводами или технологическим оборудованием;
- автономное назначение опасных работ искусственным интеллектом;
- универсальный BPMN-движок;
- произвольное создание любых таблиц и выполнение пользовательского кода;
- сложная оптимизация расписаний и многофакторный AI-планировщик.

## 3. Принципы архитектуры

### 3.1. Архитектурный стиль

Начинать с **modular monolith**. Доменные модули разделены в коде и имеют ясные интерфейсы, но разворачиваются как единое приложение. Микросервисы не вводить без измеримой технической необходимости.

### 3.2. Базовый технологический стек

| Слой | Технология | Назначение |
|---|---|---|
| Frontend | React + TypeScript + Vite | Веб-интерфейс |
| UI | Tailwind CSS + shadcn/ui либо эквивалентная доступная библиотека | Компоненты и дизайн-система |
| Backend | Python + FastAPI | API и бизнес-логика |
| Валидация | Pydantic | Контракты API и проверка входных данных |
| ORM | SQLAlchemy 2.x | Работа с данными |
| Миграции | Alembic | Версионирование схемы БД |
| Database | PostgreSQL | Основное постоянное хранилище |
| API | REST + OpenAPI | Контракт frontend/backend и внешние интеграции |
| Контейнеры | Docker Compose | Локальная воспроизводимая среда |
| Backend tests | Pytest + HTTPX | Unit/integration/API tests |
| Frontend tests | Vitest + Testing Library | Компоненты и логика |
| E2E | Playwright | Критические пользовательские сценарии |
| CI | GitHub Actions | Автоматические проверки Pull Request |

Версии зависимостей должны быть совместимыми и зафиксированными lock-файлами на этапе bootstrap. Не добавлять Redis, брокер сообщений, отдельный поисковый движок или облачные сервисы до появления конкретного сценария, который требует их.

### 3.3. Доменное разделение

Backend следует организовать по доменам, а не по типам файлов, разнесённым в одну общую папку:

- `identity_access` — пользователи, аутентификация, роли, разрешения и scope;
- `organization` — предприятия, площадки, подразделения, команды, должности;
- `personnel` — физические лица, трудовые ресурсы, назначения и членство в командах;
- `competence` — категории навыков, компетенции, шкалы, оценки и подтверждения;
- `credentials` — квалификации, сертификаты, аттестации и допуски;
- `availability` — календари, смены, доступность и резервирование;
- `work_management` — заявки, технические задания, операции и трудозатраты;
- `matching` — жёсткие ограничения, ранжирование и объяснения рекомендаций;
- `configuration` — справочники, пользовательские поля, версии конфигураций и публикация;
- `analytics` — показатели и отчёты;
- `audit` — журнал значимых действий;
- `integrations` — внешние API и синхронизация (позже).

Frontend должен иметь feature/domain-oriented структуру, общую дизайн-систему, типизированный API-клиент и единое управление состояниями загрузки, ошибок и пустых данных.

### 3.4. Модель данных и конфигурируемость

Использовать принцип **stable core + configurable metadata**:

- базовые сущности (Person, WorkforceResource, OrganizationUnit, Skill, PersonSkillAssessment, PersonCredential, WorkOrder, WorkAssignment и другие) хранить в нормализованных таблицах;
- пользовательские поля описывать метаданными с типом, валидацией, обязательностью, видимостью и правилами фильтрации;
- JSONB использовать для ограниченных конфигурационных документов и расширяемых атрибутов, но не заменять им всю реляционную модель;
- не вводить универсальную EAV-схему как основу всех данных;
- пользовательские определения и процессы должны иметь версии, состояния draft/published и проверку перед публикацией;
- архивировать справочники вместо физического удаления, если на них ссылается история.

В первой версии конфигуратора дать администратору возможность без изменения кода создавать категории компетенций, навыки, шкалы, типы документов, организационные типы и предусмотренные пользовательские поля. Универсальный конструктор сущностей и связей отложить до подтверждения реальной потребности.

### 3.5. Безопасность и достоверность данных

- Серверная проверка доступа обязательна; скрытие кнопок на frontend не является защитой.
- RBAC должен поддерживать область действия: предприятие, площадка, подразделение, собственные записи.
- Для критичных операций вести аудит: кто, когда, что изменил, старое и новое значение, причина (где требуется).
- Пароли при локальной аутентификации хранить только в виде безопасного хеша Argon2id; предусмотреть возможность OIDC/SSO позже.
- Для cookie-based сессий применять HttpOnly/Secure/SameSite, CSRF-защиту и ограничения частоты запросов.
- Файлы отдавать только через backend после проверки прав.
- Временные интервалы хранить с однозначной временной семантикой (UTC для timestamps), часовой пояс задавать для площадки/календаря.
- Формальные требования к допускам и промышленной безопасности не выдумывать: они должны быть явно настроены ответственными лицами и проверены применительно к конкретному предприятию.

**Safety gate:** обязательный действующий допуск, область его применения и обязательная квалификация проверяются на backend при назначении и повторно при начале/подтверждении работы. Рейтинг, AI и ручной выбор не имеют права обходить жёсткие ограничения.

## 4. MVP: один сквозной сценарий

MVP считается функционально завершённым, когда пользователь может пройти сквозной путь:

**Организационная структура → сотрудник → компетенция → подтверждённая оценка → действующий допуск → доступность → техническое задание с требованиями → объяснимый подбор → назначение → резервирование времени → аналитика загрузки.**

Данные должны сохраняться в PostgreSQL, переживать перезапуск и быть доступны согласно правам пользователя. Наличие макета, формы или заглушки API не считается выполнением сценария.

## 5. Этапы разработки и контрольные ворота

Этапы являются последовательностью работ, а не календарной оценкой. Переходить дальше после выполнения критериев приёмки предыдущего среза.

### Phase 0 — Project Discovery & Architecture

**Результат:** согласованные архитектура, границы MVP, доменная модель, структура репозитория и инженерные правила.

Задачи:
- сохранить HTML-прототип как baseline;
- перенести продуктовые требования, модель данных и roadmap в Git;
- оформить архитектуру и короткие ADR;
- согласовать API conventions, auth/RBAC, конфигурационный слой;
- определить структуру backend/frontend, тестирование и Docker Compose;
- зафиксировать открытые решения.

Критерии выхода:
- документы хранятся в репозитории;
- нет противоречий между scope, ER-моделью и roadmap;
- определён минимальный вертикальный срез;
- существенные архитектурные решения зафиксированы в ADR.

### Phase 1 — Foundation & Developer Experience

**Результат:** приложение запускается локально одной документированной процедурой.

Задачи:
- backend bootstrap FastAPI;
- frontend bootstrap React/TypeScript/Vite;
- PostgreSQL и Docker Compose;
- SQLAlchemy и Alembic;
- health/readiness endpoints;
- конфигурация окружений и безопасная работа с секретами;
- миграции, seed data и демонстрационная учётная запись только для development;
- lint, type-check, unit tests и сборка в GitHub Actions;
- общий layout интерфейса, навигация и дизайн-система.

Критерии выхода:
- чистый запуск по README;
- миграции применяются на пустой БД;
- frontend обращается к реальному API;
- CI блокирует PR при ошибке обязательных проверок;
- никаких секретов и реальных персональных данных в репозитории.

### Phase 2 — Identity, Organization & Access

**Результат:** безопасный вход и управляемая структура предприятия.

Задачи:
- пользовательские аккаунты и сессии;
- роли и разрешения;
- scope-права;
- предприятие, площадки, службы, подразделения, команды/бригады;
- должности и справочники;
- аудит административных изменений.

Критерии выхода:
- администратор создаёт и редактирует организацию;
- руководитель видит только свой разрешённый scope;
- backend отклоняет недопустимые запросы независимо от UI;
- значимые изменения попадают в audit log.

### Phase 3 — Personnel & Workforce Resource

**Результат:** достоверная база технических специалистов.

Задачи:
- карточка сотрудника;
- отдельная сущность назначаемого трудового ресурса;
- история организационных назначений;
- основное и дополнительное членство в командах;
- фильтрация и поиск;
- контроль видимости персональных данных.

Критерии выхода:
- CRUD работает через API и БД;
- история назначений сохраняется;
- архивирование не разрушает исторические ссылки;
- права проверяются на сервере.

### Phase 4 — Competence Management

**Результат:** настраиваемая и подтверждаемая матрица компетенций.

Задачи:
- дерево категорий и навыков;
- конструктор шкал и уровней;
- привязка навыков к сотрудникам;
- самооценка и оценка руководителя/эксперта;
- подтверждение и история оценок;
- комментарии и подтверждающие материалы;
- матрица и фильтры.

Критерии выхода:
- администратор создаёт новую компетенцию и шкалу без изменения кода;
- уровни разных шкал не сравниваются автоматически;
- самооценка отделена от утверждённой оценки;
- история оценок доступна согласно правам.

### Phase 5 — Credentials & Availability

**Результат:** система корректно знает, кто и в какой период имеет право и возможность работать.

Задачи:
- типы документов и допусков;
- записи о квалификациях и сертификатах;
- даты, срок действия, область применения и подтверждение;
- напоминания об истечении;
- рабочие календари и шаблоны смен;
- отпуска, обучение, отсутствие и доступность;
- проверка конфликтов временных интервалов.

Критерии выхода:
- просроченный документ распознаётся;
- область применения допуска учитывается;
- обязательный допуск проверяется backend;
- конфликты и часовые пояса обработаны тестами.

### Phase 6 — Work Management & Matching

**Результат:** полноценное назначение технических работ по реальным возможностям персонала.

Задачи:
- заявки и work orders;
- операции технического задания;
- ссылка на оборудование (без реализации полной EAM);
- требования к компетенциям и допускам на уровне задания/операции;
- Matching Engine;
- причины соответствия и отказа;
- назначение специалиста/бригады;
- резервирование рабочего времени;
- учёт фактических трудозатрат.

Критерии выхода:
- подбор выполняется по данным backend;
- hard constraints отделены от scoring;
- результат объясним;
- назначение повторно валидируется на backend;
- ручной override не обходит safety gate;
- конкурирующие назначения не создают двойное резервирование.

### Phase 7 — Analytics & Configurator v1

**Результат:** управленческие показатели и повседневная самостоятельная настройка.

Задачи:
- dashboard руководителя;
- загрузка и доступность;
- Skill Coverage / Skill Gap;
- предупреждения об истекающих документах;
- настройки каталогов, шкал, типов документов и организационных справочников;
- предусмотренные custom fields;
- версии конфигурации: draft → validate → publish;
- экспорт отчётов и резервная копия конфигурации.

Критерии выхода:
- показатели рассчитываются из фактических записей, формулы документированы;
- изменения конфигурации валидируются до публикации;
- опубликованную конфигурацию нельзя изменить незаметно;
- архивные записи сохраняют целостность.

**Это целевой MVP.**

### Phase 8 — Configurator Advanced & Integrations

После подтверждения MVP:
- динамические формы и представления;
- настраиваемые статусы и ограниченные workflow;
- декларативные бизнес-правила;
- настройка dashboard и отчётов;
- импорт/экспорт конфигураций между средами;
- API-коннекторы к HRMS/ERP/CMMS/EAM;
- журнал синхронизации и обработка конфликтов.

### Phase 9 — Advanced Capabilities

После накопления реальных данных:
- мобильный PWA;
- база технических знаний и опыта по неисправностям;
- планирование обучения и кадрового резерва;
- прогнозирование квалификационного дефицита;
- оптимизация смен и назначений;
- AI-помощник для поиска экспертов и объяснения Skill Gap;
- подрядчики и внешние ресурсы;
- корпоративный SSO.

AI только рекомендует и объясняет. Он не подтверждает квалификацию, не выдаёт допуски и не снимает safety gates.

## 7. Правила Git и поставки

- `main` — стабильная интеграционная ветка.
- Работа ведётся в `feature/*`, `fix/*`, `docs/*`.
- Изменения в `main` — только через Pull Request.
- Предпочтительный merge — squash merge.
- Не делать force-push в общие ветки.
- Не хранить секреты, реальные персональные данные и пользовательские файлы с ограниченным доступом.
- Для каждого PR указывать: цель, изменённые области, критерии приёмки, тесты, миграции и риски.
- Включить защиту `main`: требовать PR и успешные обязательные CI checks. Настройку защиты выполнить после появления первого рабочего CI workflow.
- Коммиты должны иметь предметные сообщения; изменения должны быть небольшими и обозримыми.

### Definition of Done

Задача не считается завершённой, пока:
1. пользовательский сценарий работает полностью, а не только визуально;
2. бизнес-правила и права проверяются на backend;
3. данные сохраняются и читаются из PostgreSQL;
4. миграции применимы на чистой БД;
5. для критичной логики есть автоматические тесты;
6. обработаны ошибки, пустые и граничные состояния;
7. документация и roadmap отражают фактическое состояние;
8. PR содержит результаты реально выполненных проверок.

## 8. Риски, которые нужно контролировать

| Риск | Мера |
|---|---|
| Преждевременный универсальный конструктор | Сначала core-модель и Configurator v1; произвольные сущности — после MVP |
| Смешение навыка, квалификации и допуска | Раздельные сущности и серверные правила |
| Обход ограничений через frontend или ручное назначение | Единый backend policy/safety service |
| Сложная матрица прав | RBAC + scope с тестами негативного доступа |
| Некорректное планирование | UTC timestamps, timezone календаря, транзакционные резервации |
| Дублирование бизнес-логики | Backend — источник истины, frontend только отображает результат |
| Разрастание EAM scope | Только ссылка на оборудование и техническое задание на MVP |
| Потеря функций прототипа | Сохранить baseline и переносить сценарии по одному |
| Ложная аналитика | Формулы KPI документировать, считать из реальных данных |
| Чрезмерная сложность стека | Modular monolith, не вводить инфраструктуру без сценария |

## 9. Открытые решения перед production deployment

Не блокируют Phase 0/1, но должны быть подтверждены до соответствующей реализации:

1. **Размещение:** локальный сервер предприятия, private cloud или публичный cloud.
2. **Режим эксплуатации:** одна организация или несколько независимых предприятий в одной инсталляции.
3. **Аутентификация:** локальные аккаунты, корпоративный OIDC/SSO либо оба варианта.
4. **Файлы:** локальное хранилище на старте и необходимость S3-совместимого storage в production.
5. **Интеграции:** какие HRMS/ERP/CMMS/EAM системы являются первыми источниками сотрудников, оборудования и заданий.
6. **Язык и локаль:** русский интерфейс в MVP; дополнительные языки и форматы дат/чисел — через i18n.
7. **Рабочее время:** правила смен, ночные смены, сверхурочные и календарные исключения определяются конфигурацией предприятия.

До подтверждения этих решений не зашивать в код локальные правовые нормы и специфические правила одного предприятия.

## 10. Следующее действие

Начать с **Phase 0 → Phase 1**, не переходя сразу к реализации всех предметных модулей.

Первый практический инженерный PR после принятия этого плана должен включать:
- окончательную структуру каталогов;
- минимальный FastAPI backend;
- минимальный React frontend;
- Docker Compose с PostgreSQL;
- Alembic и стартовую миграцию;
- health endpoint;
- базовые unit/integration tests;
- CI workflow;
- инструкции запуска в README.

После успешного чистого запуска перейти к аутентификации, RBAC и организационной структуре.
