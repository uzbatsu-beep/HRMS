# TWM — план дальнейшей разработки

**Проект:** Technical Workforce Management  
**Репозиторий:** `uzbatsu-beep/HRMS`  
**Версия плана:** 0.2  
**Дата:** 2026-11-12  
**Статус:** предложенный план; открытые архитектурные решения перечислены в конце документа.

## 1. Цель и исходное состояние

TWM — собственное конфигурируемое веб-приложение для управления внутренними техническими службами производственного предприятия: механика, электрика, энергетика, АСУ ТП, робототехника, метрология и другие инженерные подразделения.

Продукт помогает определить, какими подтверждёнными компетенциями и допусками обладают специалисты, когда они доступны, какие работы могут выполнять и почему система рекомендует конкретного исполнителя.

TWM не является payroll-системой, SCADA или полной EAM/CMMS.

### Состояние репозитория на дату плана

Проверена ветка `main`:
- `TWM_Configurable_Prototype_v0.1.html` — интерактивный одностраничный frontend-прототип;
- `README .md` — описание возможностей и ограничений прототипа;
- `README.md` в ходе текущей работы был удалён отдельным коммитом владельца репозитория; данный PR добавляет новый проектный README;
- backend, PostgreSQL, миграции, CI и автоматические тесты пока отсутствуют;
- на момент первичного аудита открытых Issues и PR не было;
- `main` не была защищена branch rules.

Прототип сохранить как baseline и использовать для переноса сценариев. Не переписывать его вслепую и не считать production-реализацией.

## 2. Продуктовый scope

### Входит в продукт
1. Организационная структура: предприятие, площадки, службы, подразделения, бригады, должности.
2. Профили сотрудников и назначаемых трудовых ресурсов.
3. Каталог специальностей и иерархическая матрица компетенций.
4. Настраиваемые шкалы оценки и история подтверждений.
5. Квалификации, сертификаты, аттестации и допуски с областью применимости и сроками.
6. Рабочие календари, смены, доступность и загрузка.
7. Заявки, технические задания, операции и требования к исполнителям.
8. Объяснимый подбор и назначение специалистов.
9. Плановые и фактические трудозатраты.
10. Аналитика квалификационного покрытия, дефицита компетенций, загрузки и рисков.
11. Конфигуратор справочников, шкал, ролей, предусмотренных пользовательских полей и ограниченных бизнес-правил.
12. API и интеграции с HRMS/ERP/CMMS/EAM на последующих этапах.

### Не входит в первый MVP
- расчёт заработной платы и полное кадровое делопроизводство;
- полноценная EAM/CMMS и полный жизненный цикл активов;
- прямое управление PLC, роботами, приводами и технологическим оборудованием;
- автономное назначение опасных работ искусственным интеллектом;
- универсальный BPMN-движок;
- произвольное создание любых сущностей и исполнение пользовательского кода;
- сложная оптимизация расписаний и автономный AI-планировщик.

## 3. Архитектурные принципы

### 3.1. Стиль
Начинать с **modular monolith**. Доменные модули разделены в коде и имеют ясные интерфейсы, но разворачиваются как единое приложение. Микросервисы не вводить без измеримой необходимости.

### 3.2. Базовый стек

| Слой | Технология |
|---|---|
| Frontend | React + TypeScript + Vite |
| UI | Tailwind CSS + shadcn/ui либо обоснованный эквивалент |
| Backend | Python + FastAPI + Pydantic |
| ORM | SQLAlchemy 2.x |
| Миграции | Alembic |
| Database | PostgreSQL |
| API | REST + OpenAPI |
| Локальная среда | Docker Compose |
| Backend tests | Pytest + HTTPX |
| Frontend tests | Vitest + Testing Library |
| E2E | Playwright |
| CI | GitHub Actions |

Версии зафиксировать lock-файлами после проверки совместимости. Не добавлять Redis, брокер сообщений, поисковый сервер или облачные сервисы без конкретного обоснованного сценария.

### 3.3. Доменные модули backend
- `identity_access` — пользователи, аутентификация, роли, разрешения, scope;
- `organization` — предприятия, площадки, подразделения, команды и должности;
- `personnel` — физические лица, трудовые ресурсы, назначения и членство;
- `competence` — категории, навыки, шкалы, оценки и подтверждения;
- `credentials` — квалификации, сертификаты, аттестации и допуски;
- `availability` — календари, смены, доступность и резервирование;
- `work_management` — заявки, технические задания, операции и трудозатраты;
- `matching` — жёсткие ограничения, ранжирование и объяснения;
- `configuration` — справочники, пользовательские поля, версии и публикация;
- `analytics` — показатели и отчёты;
- `audit` — журнал значимых действий;
- `integrations` — внешние API и синхронизация (позже).

Frontend — feature/domain-oriented структура, общая дизайн-система, типизированный API-клиент, единые состояния загрузки, ошибок и пустых данных.

### 3.4. Модель конфигурируемости
Применять **stable core + configurable metadata**:
- критичные сущности хранить в нормализованных реляционных таблицах;
- пользовательские поля описывать метаданными: тип, валидация, обязательность, видимость, поиск и фильтрация;
- JSONB применять для ограниченных конфигурационных документов и расширяемых атрибутов, но не для всей доменной модели;
- не строить универсальное EAV-хранилище как основу приложения;
- конфигурации версионировать; draft проходит валидацию до publish;
- справочники, на которые ссылается история, архивировать, а не физически удалять.

В первой версии конфигуратора администратор самостоятельно создаёт категории компетенций, навыки, шкалы, типы документов, организационные типы и предусмотренные пользовательские поля. Универсальный конструктор сущностей отложить.

### 3.5. Безопасность и целостность
- RBAC с областью действия: предприятие, площадка, подразделение, собственные записи.
- Серверная проверка разрешений обязательна; скрытие UI не является защитой.
- Аудировать изменения допусков, оценок, назначений, конфигурации и прав.
- Локальные пароли хешировать Argon2id; предусмотреть возможность OIDC/SSO.
- Для cookie-сессий применять HttpOnly/Secure/SameSite и CSRF-защиту.
- Файлы выдавать только через backend с проверкой прав.
- Хранить timestamps в UTC; часовой пояс задавать для площадки/календаря.
- Не выдумывать юридические нормы и правила промышленной безопасности: их задаёт и подтверждает ответственная сторона предприятия.

**Safety gate:** обязательный действующий допуск, его область применения и обязательная квалификация проверяются backend при назначении и повторно при начале/подтверждении работы. Рейтинг, AI и ручной выбор не могут обходить эти ограничения.

## 4. MVP — один сквозной пользовательский путь

MVP завершён, когда пользователь проходит путь:

**Организационная структура → сотрудник → компетенция → подтверждённая оценка → действующий допуск → доступность → техническое задание с требованиями → объяснимый подбор → назначение → резервирование времени → аналитика загрузки.**

Данные сохраняются в PostgreSQL, переживают перезапуск и доступны согласно правам. Макет, форма или stub API не считаются выполнением сценария.

## 5. Этапы разработки и критерии выхода

### Phase 0 — Discovery & Architecture
**Результат:** согласованные границы MVP, архитектура, доменная модель, структура репозитория и инженерные правила.

Работы:
- сохранить HTML-прототип как baseline;
- перенести требования, модель данных и roadmap в Git;
- подготовить architecture document и ADR;
- зафиксировать API conventions, auth/RBAC и стратегию конфигураций;
- определить структуру frontend/backend, тестирование и Docker Compose;
- составить список открытых решений.

Критерии выхода: документация находится в Git, требования и ER-модель согласованы, MVP имеет границы, архитектурные решения зафиксированы.

### Phase 1 — Foundation & Developer Experience
**Результат:** приложение воспроизводимо запускается локально.

Работы:
- FastAPI bootstrap;
- React/TypeScript/Vite bootstrap;
- PostgreSQL и Docker Compose;
- SQLAlchemy и Alembic;
- health/readiness endpoints;
- конфигурация окружений и секретов;
- миграции и seed data;
- lint, type-check, unit tests и build в GitHub Actions;
- общий layout, навигация и базовая дизайн-система.

Критерии: чистый запуск по README, миграции на пустой БД, frontend работает с реальным API, CI блокирует PR при ошибках, секретов и реальных персональных данных в Git нет.

### Phase 2 — Identity, Organization & Access
**Результат:** безопасный вход и управляемая структура предприятия.

Работы: аккаунты/сессии, роли и разрешения, scope-права, предприятие/площадки/службы/подразделения/команды, должности, аудит.

Критерии: администратор управляет структурой; руководитель видит только свой scope; backend отклоняет неразрешённые запросы; изменения аудируются.

### Phase 3 — Personnel & Workforce Resource
**Результат:** достоверная база технических специалистов.

Работы: карточки сотрудников, отдельный WorkforceResource, история назначений, членство в командах, поиск, фильтрация и защита персональных полей.

Критерии: CRUD через API/БД, история сохранена, архивирование не ломает связи, доступ проверяется сервером.

### Phase 4 — Competence Management
**Результат:** настраиваемая и подтверждаемая матрица компетенций.

Работы: дерево категорий/навыков, конструктор шкал, оценки, подтверждение руководителем/экспертом, история, доказательства, матрица и фильтры.

Критерии: новую компетенцию и шкалу можно создать без кода; разные шкалы не сравниваются автоматически; самооценка отделена от утверждённой оценки.

### Phase 5 — Credentials & Availability
**Результат:** достоверные допуски и доступность персонала.

Работы: типы документов, записи и файлы, сроки и область действия, напоминания, календари, смены, отсутствия, доступность, конфликты интервалов.

Критерии: просроченные документы распознаются; область допуска учитывается; safety gate enforced backend; часовые пояса и конфликты покрыты тестами.

### Phase 6 — Work Management & Matching
**Результат:** назначение технических работ по возможностям персонала.

Работы: заявки, work orders, операции, ссылки на оборудование, требования к навыкам/допускам, Matching Engine, причины рекомендаций, назначения, резервирование времени и трудозатраты.

Критерии: подбор идёт по данным backend; hard constraints отделены от scoring; результат объясним; ручной override не обходит safety gate; двойное резервирование предотвращается транзакционно.

### Phase 7 — Analytics & Configurator v1
**Результат:** управленческие показатели и самостоятельная настройка каталогов.

Работы: dashboard руководителя, загрузка, Skill Coverage/Skill Gap, истекающие допуски, настройка каталогов/шкал/типов документов, поддерживаемые custom fields, draft/validate/publish конфигурации, экспорт.

Критерии: метрики рассчитываются из реальных данных; формулы документированы; конфигурация валидируется до публикации; история сохраняется.

**Phase 7 — целевой MVP.**

### Phase 8 — Configurator Advanced & Integrations
Динамические формы и представления, статусы и ограниченные workflow, декларативные бизнес-правила, пользовательские dashboard, перенос конфигураций, API-коннекторы HRMS/ERP/CMMS/EAM, журнал синхронизации.

### Phase 9 — Advanced Capabilities
Мобильный PWA, база технических знаний, планирование обучения и кадрового резерва, прогноз Skill Gap, оптимизация смен, AI-помощник, подрядчики и корпоративный SSO. AI не подтверждает квалификации и не отменяет safety gates.

## 7. Git workflow и Definition of Done

- `main` — стабильная интеграционная ветка.
- Работа в `feature/*`, `fix/*`, `docs/*`.
- Все изменения в main — через Pull Request.
- Предпочтительный merge — squash.
- Не использовать force-push в общие ветки.
- PR описывает цель, изменённые области, критерии приёмки, тесты, миграции и риски.
- После появления CI включить branch protection для main: PR и обязательные CI checks.
- Не хранить секреты, реальные персональные данные и защищённые пользовательские файлы.

Задача завершена, только когда сценарий работает end-to-end, backend проверяет права и бизнес-ограничения, данные сохраняются, миграции применяются с чистой БД, критичная логика покрыта тестами, обработаны ошибки/пустые/граничные состояния, документация отражает фактическое состояние.

## 9. Открытые решения

До production deployment подтвердить:
1. Размещение: локальный сервер, private cloud или public cloud.
2. Модель установки: одна организация или несколько независимых предприятий.
3. Аутентификация: локальные аккаунты, OIDC/SSO или оба варианта.
4. Хранение файлов: локальное или S3-совместимое.
5. Первые внешние источники сотрудников, оборудования и заданий (HRMS/ERP/CMMS/EAM).
6. Языки и локали: русский в MVP, дальнейшая i18n.
7. Правила смен, ночной работы, сверхурочных и исключений — конфигурация конкретного предприятия.

Эти вопросы не блокируют архитектурную подготовку и bootstrap. Не зашивать локальные юридические и safety-нормы без подтверждённого требования.

## 10. Следующее действие

Начать с Phase 0 → Phase 1. Первый инженерный PR после принятия плана должен включать:
- структуру каталогов;
- минимальный FastAPI backend;
- минимальный React frontend;
- Docker Compose с PostgreSQL;
- Alembic и стартовую миграцию;
- health endpoint;
- unit/integration tests;
- GitHub Actions CI;
- инструкции запуска.

Затем реализовать аутентификацию, RBAC и организационную структуру.
