# TWM G6 — план нагрузочных и многопользовательских испытаний

**Статус:** схема приёмки. Реальные SLO/p95, мощность сервера, состав
пользователей и лимиты должны быть утверждены до промышленного пилота.

## Автоматическая CI-проверка

`ops/load_probe.py` безопасно ограничен loopback и GET
`/api/v1/health/{live|ready}`; откажет в удалённом URL и в проверке
изменяющих API. 160 запросов, параллелизм 8, условный порог p95 <= 1500 мс,
0 HTTP-ошибок. Выводит JSON с p50/p95/max и error_rate. Это
**smoke-test устойчивости**, не замена тесту производительности продукта.

## Обязательный план замеров на отдельном staging-контуре

1. Утвердить сценарии и долю запросов для каждой роли: обзор Dashboard,
   глобальный поиск персонала, 100/1000/10000 сотрудников, подбор кандидатов,
   проверка допусков, чтение истории, согласование и назначение бригады.
2. Создать 100% синтетические многоотраслевые данные (несколько tenants,
   подразделений и ролей). Запретить генерацию реальных ФИО/документов.
3. Замерить 1/10/25/50 одновременных сессий с устойчивой нагрузкой;
   ramp-up, 20-мин steady state, всплеск и 1-час soak. Параметры
   согласовать с бюджетом CPU/RAM/IOPS.
4. Измерять p50/p95/p99 (по каждому endpoint и сквозному пользовательскому
   действию), RPS, error rate, 409 на гонках, CPU/RAM, PostgreSQL
   connections, lock-wait, slow-query, размер индексов и autovacuum.
5. Отдельно повторить PR #31 race scenarios: одновременное назначение
   одного специалиста на пересекающиеся наряды; ни двойной брони,
   ни пропуска hard gates быть не должно.
6. Отдельный chaos/DR сценарий: перезапуск API и БД, timeouts, потеря
   соединения, недоступное хранилище backup; проверить логи и восстановление.
7. Зафиксировать исходную конфигурацию, коммит, миграцию, размер
   синтетической БД, статистику и пределы уверенности. Предложить и
   утвердить SLO, повторить замер после оптимизаций.

**Граница:** метрики CI здоровья не позволяют оценить производительность
подбора, поиска или записи на тысячах сотрудников. Без указанных
измерений OPS-09 остаётся открытым для пилота.

## Локальный baseline INF-01 (ещё не выполнен)

Для выбранного **типа** стенда (отдельный Windows/Linux ПК) рекомендованы 6–8 логических CPU, 16 ГБ RAM и 120–256 ГБ свободного SSD; это **гипотеза для тестирования**, а не доказанная capacity. Начать с 1/5/10 синтетических сессий и 100/1000 вымышленных сотрудников; фиксировать p50/p95/p99 по реальным маршрутам и p95 сквозных UI действий, CPU/RAM/IOPS и PostgreSQL locks. Затем на более мощном стенде пройти 25/50 сессий и 10000 записей. Отдельно измерить latency и рост таблицы audit при активности PR #36 **после его слияния и тестового обновления**.

`ops/load_probe.py` по `/health/ready` даёт только bounded synthetic readiness smoke, не доказывает обрабатываемость 50 пользователей и не устанавливает SLO. `INF-07` открыта; [Issue #37](https://github.com/uzbatsu-beep/HRMS/issues/37), [индекс](DOCUMENTATION_INDEX.md).
